# Specification directory and scaffolding contract

## Purpose and authority

This contract defines the default `.spectrum/` layout and the boundary of scaffolding. Product behavior, information architecture and web experiences belong to `product/`. Engineering knowledge records implementation decisions and discoveries as the project develops.

The configuration in `config.json` or an explicitly selected profile maps the actual sources. These are default destinations for new documents; existing repositories can retain their own paths through an explicit source mapping. A path change preserves document IDs, acceptance criteria and policy meaning.

## Default layout

```text
.spectrum/
  config.json
  overview.md
  schemas/                         # Installed schema definitions
  rules/                           # Scoped repository instructions
  product/
    specification_structure.md     # This layout and scaffolding contract
    information_architecture/
      objects/{schema.json,data.tsv}
      surfaces/{schema.json,data.tsv}
      surface_structure/{schema.json,data.tsv}
      menus/{schema.json,data.tsv}  # Optional desktop inventory
    feature_inventory/
      feature_categories/{schema.json,data.tsv}
      features/{schema.json,data.tsv}
      interactions/{schema.json,data.tsv}
    feature_specs/<category>/
      contracts/*.toml
      flows/*.md
      <feature_id>/<interaction_id>.md
    website/                       # Optional web product experience
      route_map/routes/{schema.json,data.tsv}
      page_contracts/<page>/
        contract.toml
        layout.md
        flow.md
        spec.md                    # Optional page experience detail
  engineering/
    <platform>/decisions/<YYYY-MM>/<dated-decision>.md
    ...                            # Knowledge created as the project develops
```

## Required and optional content

- Configuration declares the selected inventory/schema pairs and document sources. The engine requires nonempty inventory and document source lists; it does not require every module in this tree.
- A feature bundle uses category, feature and interaction records, with one Markdown specification per documented interaction. Referenced IA records, contracts and flows must exist.
- Web routes and page contracts are product documents under `product/website/`. A selected page bundle contains a TOML contract, layout and flow; its experience spec is optional. A project with no web experience can omit that module and its configuration entries.
- Desktop menus and custom inventories are optional and need explicit source mappings when selected.
- Engineering articles are authored when implementation and operations produce useful knowledge. No fixed architecture, implementation, boundary, runbook or governance article is generated by default. An ADR template supports a specific proposed decision and its alternatives; it does not approve that decision.
- Overview, rules and installed schemas support the selected bundle. Credentials, runtime caches, local execution state and production data stay outside canonical specification files.

## Template ownership

`@spectrum/spec-engine/templates` owns the reusable template catalog and files. `catalog.json` maps template IDs to suggested output paths. FI schema templates extend engine-owned base schemas; repository extensions add local columns. Actual product records belong to the repository, not to the template library.

Template updates do not silently rewrite installed specifications. Changes to installed schema definitions and their shipped templates are reviewed together. The self-repository checks that its installed schema and layout definitions match the shipped definitions.

## Current scaffolding behavior

The available API is read-only:

1. `listTemplates()` returns the catalog.
2. `loadTemplate(id)` exposes the template body and destination pattern.
3. The author supplies consistent IDs, source mapping and product statements.
4. `renderTemplate(id, values)` returns `{ path, content }` without writing files.
5. The caller reviews the outputs, creates the selected files through its separately authorized workflow and runs the shared repository checker.

All referenced template values are required. Undecided prose may use `TBD`; confirmed absence uses `-`. A path placeholder is one safe filename segment. TSV values occupy one cell; JSON, YAML and TOML string substitutions preserve their structure. Repositories retain their own vocabulary and IDs.

Rendering never approves a document, executes customer acceptance criteria, connects an integration or makes a model call. Initial review states are draft or Proposed; declared implementation states are planned. Structural success is separate from implementation and execution evidence.

## Initialization boundary and open decisions

A CLI `init` command, automatic directory creation, an installer, overwrite/merge behavior and transactional file application are not implemented. The template API has no writer or overwrite option. Brownfield adoption currently uses explicit source mapping; it does not relocate existing documents automatically.

A future writer needs its own approved contract for file selection, existing-file conflicts, permissions, atomicity, recovery and validation. This document does not claim those policies have been implemented or authorize replacing customer files.

## Acceptance criteria

- [ ] **AC-1:** Default web route and page outputs are inside `.spectrum/product/website/`.
- [ ] **AC-2:** A connected rendered starter bundle passes the real repository checker, including local document links and adjacent schema references.
- [ ] **AC-3:** Product IDs, acceptance statements and declared review/implementation states remain separate from executed evidence.
- [ ] **AC-4:** Rendering rejects missing values, unsafe path segments and multi-cell TSV values without writing to the repository.
- [ ] **AC-5:** Optional modules are selected through configuration; engineering articles are not required scaffolding output, and ADR creation remains tied to an actual decision.

## Verification boundary

Template regression tests render into an isolated temporary repository and use the actual parser and checker. They verify nested website destinations, schema reference resolution, content escaping and installed-definition consistency. These tests validate the default blueprint; they do not restrict supported brownfield source paths or prove an unimplemented initializer.
